# Operations

Day-two procedures for a running Aarogya Aarohan deployment.

---

## Releasing a new version

Application repositories build container images in their own CI and push them with immutable tags. Deploying is a change in this repository:

```bash
# components/<app>/overlays/<env>/kustomization.yaml
images:
  - name: <image>
    newTag: v1.2.3
```

1. Open a pull request that changes `newTag` for the target environment.
2. Merge. ArgoCD detects the change, renders the overlay and Kubernetes performs a rolling update.
3. Watch the Application reach `Synced` / `Healthy` and check the dashboards for error rate and latency.

Change staging first, verify, then change production in a separate pull request. Both environments' Applications track the same branch, so the overlay file is what separates them.

**Ship code and config together.** If a release needs a new ConfigMap key or environment variable, bump the image tag in the same pull request. A config that references code not yet in the running image will crash the pods.

## Rolling back

Revert the commit that changed `newTag` and merge. This is the only durable rollback: ArgoCD `selfHeal` reverts manual changes such as `kubectl set image` or `kubectl rollout undo` within seconds.

> **HAPI FHIR schema.** HAPI migrates its database schema on start-up. Rolling HAPI back across a version that changed the schema may not be safe. Take a database backup before upgrading HAPI, and check the HAPI FHIR release notes for migration tasks.

## Emergency changes

Every change goes through Git, including emergencies. To pause something, ship the brake in a pull request (for example `suspend: true` on a CronJob, or a feature flag set to off). A `kubectl patch` will be reverted by `selfHeal`.

To stop ArgoCD reverting a resource while you debug, disable auto-sync on that one Application in the ArgoCD UI, and re-enable it when done.

## Backups and restore

| Data | Backup | Restore |
|---|---|---|
| PostgreSQL (all tenants' FHIR data, Keycloak) | Automated daily backups (7 retained in staging, 30 in production) and point-in-time recovery with 7 days of transaction logs | Restore to a **new instance** at a point in time, verify, then repoint the DB proxy / connection string. A restore covers all tenants on the instance. |
| Tenant media buckets | Object versioning; non-current versions kept 90 days | Restore an earlier object version |
| Keycloak realms | Contained in the PostgreSQL backup; per-realm export with `scripts/export-keycloak.sh` | Realm import |
| Git (this repo) | The Git host | Re-clone; ArgoCD re-syncs |
| Terraform state | Versioned state bucket | Restore an earlier object version |

Rehearse a restore into a scratch instance at least once per quarter and record the time it took.

**Per-tenant recovery.** Because tenants share one database, recovering a single tenant means restoring into a scratch instance and exporting that tenant's partition with FHIR `$export`, then importing it into the live partition.

## Rotating a secret

1. Add a new version of the secret in the cloud secret store.
2. Force a refresh, or wait up to one hour (`refreshInterval: 1h`):
   ```bash
   kubectl -n <ns> annotate externalsecret <name> force-sync=$(date +%s) --overwrite
   ```
3. Restart consumers that read the secret only at start-up:

| Secret | Restart |
|---|---|
| HAPI database credentials | `deploy/hapi-fhir` |
| Keycloak database credentials, admin | `statefulset/keycloak` |
| Tenant credentials bundle | `deploy/fhir-gateway`, `deploy/fhir-gateway-cron` |
| Dashboard tenant map | `deploy/arogyam-dashboard` |

Database and Keycloak admin passwords are generated by Terraform: `terraform taint` the relevant `random_password` resource and run `make plan` / `make apply` for the environment, which updates both the database user and the secret entry, then restart the consumers.

The ArgoCD repository deploy key is rotated by adding a new deploy key on the Git host, adding it as a new secret version and re-applying the `argocd` Terraform stack (it reads the latest version on each apply). Rotate it at least quarterly.

## Monitoring and alerting

- **Dashboards** (defined in `terraform/envs/monitoring/dashboards/`): platform overview, per-tenant traffic, pod restarts and resources, HAPI JVM, Keycloak, nodes, PostgreSQL, buckets, firing alerts, availability.
- **Alert policies** exist once per environment: ingress 5xx ratio, p95 latency, container restart storms, deployments with no ready replicas, database disk / CPU / availability, node pressure, metrics collection stopped, certificate expiry. They can be toggled with `alerts_enabled`.
- **Uptime checks** probe the public FHIR, Keycloak and dashboard endpoints.

All of this is Terraform. Do not create dashboards or alerts in the cloud console; if you do, import them into `terraform/envs/monitoring` so Git stays the complete record.

## Troubleshooting

| Symptom | Where to look |
|---|---|
| Pod in `CrashLoopBackOff` | `kubectl describe pod` (OOMKilled? probe failures?), `kubectl logs --previous`, then the ArgoCD history: what changed? A ConfigMap that refers to a class or setting not in the running image is a common cause. |
| HAPI restarts under load with exit code 143 | Liveness probe timing out; raise `timeoutSeconds` and `failureThreshold` on the probes |
| Users see 502/504 | Load balancer backend health → ingress-nginx logs → backend pod readiness → HAPI latency → database CPU and connections |
| One tenant cannot log in | Registry entry present? Gateway and dashboard restarted after onboarding? Realm redirect URIs set? Token contains `partition_id`? |
| FHIR returns 403 | Decode the token; `partition_id` must match the URL tenant, and FHIR roles must be present |
| A pod gets 403 from a cloud API | Which ServiceAccount is it using, and is the IAM binding on exactly that principal (project, namespace, name)? |
| Outbound HTTPS fails from pods but works from the bastion | NetworkPolicy → NAT → DNS → certificate chain. For servers with incomplete chains, mount the missing CA and set `NODE_EXTRA_CA_CERTS`; keep TLS verification on. |
| ArgoCD Application `OutOfSync` / `Degraded` | Read the diff in ArgoCD; render locally with `kustomize build`; check the AppProject allows the destination; check for manual edits |
| `kubectl` on the bastion touches the wrong cluster | Always pass `--context` explicitly |
| Terraform for the `argocd` stack hangs from a laptop | The cluster APIs are private; run it from the bastion |
